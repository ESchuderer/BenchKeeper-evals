# Anthropic engineering guidance against BenchKeeper's rules and skills

Ticket: ESchuderer/BenchKeeper#382. Tier: research. No change to `plugins/` is made here. Read on 2026-10-27.

## Question

What do Anthropic's engineering posts, prompting guidance and Claude Code docs say that BenchKeeper's global rules, skill texts and tier model (`plugins/benchkeeper/rules/`, `plugins/benchkeeper/skills/`) do not yet follow, or contradict?

## Short answer

Most of BenchKeeper already matches the guidance: short rules files, no emphasis words, evidence in the done report, a fresh-context restart when a build drifts, user-only skills for side effects, balanced trigger cases. Five items contradict a source, and the first one contradicts BenchKeeper itself. In rank order:

1. `rules/project.md:2` asks open questions in one message when scope is open. `skills/workflow/SKILL.md:19` grills the user in rounds for every standard and full task, though the standard tier is defined as "approach clear". Anthropic's memory docs say contradicting instructions make Claude "pick one arbitrarily".
2. Zero-exception rules ("never skip a check or use `--no-verify`", "never run `terraform apply`", "never bypass a hook") exist only as prose. Claude Code best practices say a rule with no exceptions belongs in a deny rule or hook, because prose is a guideline Claude may decide does not apply.
3. "Two or more independent items: one subagent per item" has no size condition. Anthropic's Opus 5 guidance and the multi-agent post say to scale delegation to the task and not to delegate what a few tool calls finish.
4. The review step has no round cap and no scope line, while Anthropic says a reviewer "will always find something".
5. The skill evaluations measure trigger rate only, once per case, with no no-plugin baseline. Anthropic documents `claude plugin eval` with a baseline delta.

Confidence: medium. The Claude Code docs, prompting pages and `claude plugin eval` page were read in full text (`Read` of the saved fetch). The `anthropic.com/engineering` posts were read through a summarizing fetch, not as raw text (see Unverified). Every effect below is an expectation from the cited guidance, not a measurement on BenchKeeper.

## Already follows

- No ALL-CAPS emphasis words in `rules/` or `skills/` (grep for MUST, NEVER, ALWAYS, CRITICAL, IMPORTANT found none). Best practices: emphasis makes Claude "over-apply the rule".
- Rules files are 8 and 3 lines; the guidance target is under 200 lines per instruction file.
- The done report carries each check's command and result (`workflow/SKILL.md:23`). Best practices: ask Claude for evidence, not "all tests pass".
- Fresh-context restart when a build drifts from the plan (`full-tier.md:10`), matching "after two failed corrections run `/clear`".
- Side-effect skills are user-only (`disable-model-invocation: true` on `tier`, `maintaining-repos`, `orchestrating-projects`, `setting-up-projects`), as the docs recommend for workflows with side effects.
- Text from other authors is data, not instructions (docs pass step 3, the worker spec). Consistent with the auto-mode post's input probe.
- Coordinator verifies worker reports instead of trusting them (`orchestrating-projects/SKILL.md:42`), consistent with the long-running apps post's finding that generators praise their own work.
- Research notes go to a scratch directory outside the repository (`research.md:3`), matching structured note-taking.
- UI changes are checked in a browser (`software.md:56`), matching the long-running agents post's end-to-end browser testing.
- Balanced trigger cases (positive and negative) in `plugins/benchkeeper/evals/skill-workflow.json`.
- `/doctor prompt-audit` and `/skill-doctor` are already part of `maintaining-repos` (`SKILL.md:16`).
