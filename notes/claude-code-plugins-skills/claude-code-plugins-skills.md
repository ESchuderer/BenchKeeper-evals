# Claude Code docs against BenchKeeper's plugin, skills and library

Checked 2026-10-27. Ticket: [#380](https://github.com/ESchuderer/BenchKeeper/issues/380). Nothing under `plugins/`, `app/` or `.github/` changed.

## Question

Which documented Claude Code features for plugins, marketplaces, skills (frontmatter, invocation control, bundled files), subagents, MCP, slash commands, output styles and `claude plugin` validation or evaluation are unused or misused by `plugins/benchkeeper/`, `.claude-plugin/` and `app/src/skills.mjs`? Rank the improvements by value and effort, and mark what conflicts with the merged decision note [skill-entry-points](../../evaluations/practices/skill-entry-points.md).

## Short answer

The manifest, marketplace file and skill frontmatter are valid: `claude plugin validate plugins/benchkeeper --strict` passes with no warning (run locally on Claude Code 2.1.308). The gaps are in checking and measuring, not in missing components:

1. The documented check `claude plugin validate .` runs at the repository root and reads only `marketplace.json`, so the plugin's skills and hooks are validated by nobody in CI. The plugin's mod test (`claude plugin test`) also runs in no workflow.
2. The lite level has an unmeasured trigger rate because `evaluations/practices/lite-install.md` assumes a plugin cannot inject always-on instructions. The docs describe such a channel (a plugin `SessionStart` hook). That premise conflicts with the docs and should be re-read; the decision in that note (lite ships) is not contradicted.
3. `claude plugin eval` provides what that note's missing measurement needs (plugin alone, isolated home, no `CLAUDE.md`, a no-plugin arm). It is not used. The existing `evals/*.json` files are ignored by it, so both formats can live side by side.
4. Six trigger cases for `maintaining-repos` cannot fail while the skill stays user-only, because it is not listed to the model and calls to it are blocked.
5. `app/src/skills.mjs` has one small mismatch with the docs: its untracked-skill listing does not require a `SKILL.md`, so a skills-directory plugin folder would be listed as a skill (inferred, not run).

No conflict with `skill-entry-points.md`: the docs read for this ticket support its decision and firm up two of its "inferred" lines (see the last section). Subagents, MCP servers, output styles, `commands/`, `bin/`, monitors and plugin dependencies were checked and are not worth adding (table at the end).

## Considered and rejected

| Feature | Docs | Why not |
|---|---|---|
| `dependencies` on Ponytail or Matt Pocock's plugin | [dependencies](https://code.claude.com/docs/en/plugins/dependencies.md) | Both come from other marketplaces, which need `allowCrossMarketplaceDependenciesOn` in BenchKeeper's marketplace file; a dependency declared in `plugin.json` and not allowlisted installs without the dependency and the plugin then fails to load. It would also end "plugin alone" for lite. The skills name them "when installed" on purpose |
| Output style with `force-for-plugin` | [output styles](https://code.claude.com/docs/en/output-styles.md) | It overrides the user's style on every enable and drops the coding instructions unless `keep-coding-instructions: true`. A task-kind rule is not a response format |
| `skillOverrides` for the five plugin skills | [skills](https://code.claude.com/docs/en/skills.md) | The page says plugin skills are not affected. For installed library skills (project skills) see the `app/src/skills.mjs` section below |
| `claude plugin tag` and `<name>--v<version>` tags | [dependencies, release tag](https://code.claude.com/docs/en/plugins/dependencies.md) | Only constraints from a dependent plugin resolve against these tags. Nothing depends on BenchKeeper; the `setup-v<major>.<minor>` tags stay |
| Plugin MCP servers (`.mcp.json`) | [components](https://code.claude.com/docs/en/plugins/components.md) | The plugin needs none. The repository's Playwright server belongs to the project, not the plugin |
| `commands/`, `bin/`, monitors, themes, `settings.json` (`agent` key) | [components](https://code.claude.com/docs/en/plugins/components.md) | `commands/` is the older format that skills supersede. No script, monitor, theme or main-thread agent is needed; the `agent` default would change every session |
| Skill `hooks` frontmatter, `context: fork`, `when_to_use`, `arguments`, `paths`, `model`, `effort` | [skills](https://code.claude.com/docs/en/skills.md) | Skill hooks stay registered for the rest of the session, so they cannot end at an approval. The other fields add no behavior the five skills lack (`workflow`'s description is 318 characters, far under the 1,536 cap). `paths` for `designing-technical-uis` could narrow when it is listed, but the folder `AGENTS.md` pointer already scopes it and works in Codex |
| Redundant `"skills": "./skills/"` in `plugin.json` | [manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md) | `skills/` is scanned by default and the key adds to it; harmless, and removing it saves nothing |
| Hooks file named `hooks/claude-tier.json` instead of `hooks/hooks.json` | [mods reference, files](https://code.claude.com/docs/en/plugins/mods/reference.md) | The docs list `hooks/hooks.json` with `modules`. The validator accepts the manifest `hooks` path and reads the module (observed). No session test covers it. The reason for the current name (for example Codex) was not checked |

## `app/src/skills.mjs` against the docs

`skills.mjs` reads the state of the project's installed skills and plans update, reset, remove and adopt. It reads only, and the docs bear on it in two places.

- Untracked listing (`subfolders()`, `app/src/skills.mjs:14`, used by `projectSkills` and `globalUntracked`). It returns every directory under an agent's skills folder whose name matches a pattern, without checking for a `SKILL.md`. A folder under a project's or the user's `.claude/skills/` that holds `.claude-plugin/plugin.json` is a skills-directory plugin ([loading reference](https://code.claude.com/docs/en/plugins/loading.md)), not a skill, so it would be listed as an untracked skill. Inferred from the code and the docs, not run. Whether the remove path offers it was not checked. Value low, effort low (require `SKILL.md`, as `globalSkills` in `app/src/steps/global.mjs` does).
- Turning a skill off. `project apply --disable <name>` moves the folder to `.benchkeeper/disabled/` (`app/src/steps/project.mjs:380-401`), which works for every agent. For Claude Code, `skillOverrides` with `"off"` or `"name-only"` hides a project skill, or drops its description from the listing, without moving the folder ([skills](https://code.claude.com/docs/en/skills.md)). It does not reach Codex, Gemini CLI or Copilot CLI, and which settings file holds it was not checked, so it is an option for a Claude-only "name-only" state (cheaper listing, still typeable), not a replacement. Value low, effort medium.

## Check against the decision note on skill entry points

Decision to check: keep all five skills, no wrapper skills ([skill-entry-points.md](../../evaluations/practices/skill-entry-points.md)). Nothing read for this ticket contradicts it. Statements that support it:

- A call to a `disable-model-invocation` skill is blocked, and the skill's description is not in context ([skills](https://code.claude.com/docs/en/skills.md), invocation table). This firms up the note's "inferred, not tested" line that a user-only skill cannot be started by another skill.
- A user-only skill cannot be preloaded into a subagent ("preloading draws from the same set of skills Claude can invoke", [subagents](https://code.claude.com/docs/en/sub-agents.md)). A wrapper block behind a user-only skill would need to be model-invoked, as the note says.
- The skills page has no statement that one skill may call another through the `Skill` tool (the whole page was read), which matches the note's "silent" row. The 1% listing budget and the 1,536-character entry cap match the note.
- The note's decision that `tier` keeps its name rests on the tier band hook matching `benchkeeper:tier`. Docs: a plugin skill's command is `/<plugin>:<name>` and a frontmatter `name` replaces the last segment, so renaming the skill changes the command and the hook no longer matches. This supports the note's "a rename or split breaks the tier band".

Where this ticket touches other notes:

- `lite-install.md` (not the entry-point note): its premise "a plugin cannot ship always-on instructions" is true for a root `CLAUDE.md` and false as a general statement, because of the `SessionStart` hook (rank 2). Its decision (lite ships, trigger rate unverified) stands.
- `skill-entry-points.md` rows for "Reached by" and the trigger-eval paragraph stay correct. Rank 4 adds that the six `maintaining-repos` cases cannot fail; the note already says they are all negative.

## Unverified

- Whether `claude plugin validate` and `claude plugin test` need a login or network on a CI runner. Both ran locally while signed in; the docs say only `plugin test` needs no session, sign-in or network.
- How CI should install a pinned Claude Code. Not looked up.
- Whether a `SessionStart` hook that prints `rules/project.md` makes the model call `benchkeeper:workflow` more often than the description does. Not run. Also unchecked: hook behavior on Windows for the shell form, and the full `SessionStart` input schema (the `SessionStart` section of the hooks page was cut off in the part read).
- Which of `claude plugin details` (about 524 tokens) and the docs (zero for user-only skills) matches what `/context` shows.
- Whether `benchkeeper eval` tolerates case folders next to its JSON files in `plugins/benchkeeper/evals/`. Only the reverse was observed (`plugin eval` ignores the JSON).
- Whether Codex reads plugin `agents/` or output styles, and how Gemini CLI and Copilot CLI treat `disallowed-tools` or other Claude-only frontmatter.
- Precedence between `CLAUDE_CODE_SUBAGENT_MODEL` and an agent's `model` field.
- Anthropic's directory rules: the validator said its directory checks are a subset and the portal applies more.
- No manifest field for a minimum Claude Code version was found in the fields table, so the Claude Code version the plugin's mod and `userConfig` need (the docs give version floors for single features, for example `/config` rows from 2.1.269) was not derived.
- The last 16,349 characters of the subagents page were not read, and the hooks page past character 100,000 (of 282,608).
- The issue the entry-point note cites about coordinator mode (anthropics/claude-code#82237) was not re-checked.
