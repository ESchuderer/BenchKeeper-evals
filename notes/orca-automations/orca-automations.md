## Answers to the four open questions

### 1. Interactive terminal session or non-interactive command?

Answer: an interactive terminal session in a pseudo-terminal. Not `claude -p`.

- Docs: a reused run "continue[s] in the previous live automation terminal instead of starting from a blank terminal each time" (https://www.onorca.dev/docs/cli/automations, section "Reuse an existing automation session"). Agents that read the prompt after startup get it typed into the terminal "once they are ready", and "Agents that take the prompt on the command line, such as Claude and Codex, were never affected" (same page, section "Choose where runs happen"). The Settings page lists "automations" among agents Orca launches that "skip their 'Do you trust this folder?' prompt" (https://www.onorca.dev/docs/settings, agent settings section). On each fresh run Orca "starts from the host's default Arguments for that agent and appends the extras" (docs automations page). The docs never use the words "interactive", "non-interactive", `-p` or `--print` for automations.
- Source: the run record has `sessionKind: 'terminal'` ([automations-types.ts#L150](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/automations-types.ts#L150)). The launcher is `terminalOnly: true` and throws "An automation starts a terminal agent only." for any other surface ([headless-automation-agent-launch.ts#L28](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/headless-automation-agent-launch.ts#L28), [#L74](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/headless-automation-agent-launch.ts#L74), [#L116-L120](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/headless-automation-agent-launch.ts#L116-L120)). For `claude` the prompt mode is `argv` ([tui-agent-config.ts#L28-L30](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/tui-agent-config.ts#L28-L30)), and the launch command is the agent's configured command, then the extra agent arguments, then the quoted prompt as a positional argument ([tui-agent-startup.ts#L96-L105](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/tui-agent-startup.ts#L96-L105)). The shared startup code contains no `-p` for Claude (read of those lines).
- Desktop path (the one a local automation with `schedulerOwner: local_host_service` takes, per the live `list --json` field; the file above is the serve-mode path): the main process sends a dispatch request to the renderer, which calls `launchAgentBackgroundSession` with the agent, prompt and extra agent arguments ([automation-dispatch-handler.ts#L169-L174](https://github.com/stablyai/orca/blob/v1.4.237/src/renderer/src/hooks/automation-dispatch-handler.ts#L169-L174)). That function builds the same startup plan (`buildAgentStartupPlan`, [launch-agent-background-session.ts#L84](https://github.com/stablyai/orca/blob/v1.4.237/src/renderer/src/lib/launch-agent-background-session.ts#L84), which wraps the shared `tui-agent-startup` read above) and spawns a PTY with `window.api.pty.spawn` and a terminal tab ([#L174](https://github.com/stablyai/orca/blob/v1.4.237/src/renderer/src/lib/launch-agent-background-session.ts#L174)). It has no structured-chat or native-chat branch (a search of that file for `native`, `structured` and `chat` found none). So the chat-default setting does not apply to automations on either path.
- Qualifier: the launch command is the host's default Command and Arguments for the agent, which the user can edit (https://www.onorca.dev/docs/settings, "Per-agent launch defaults"), then the automation's extra agent arguments, then the prompt. "No `-p`" holds for the default configuration and for the extras Orca accepts (model, effort, `--add-dir`; the docs say "Permission, config, prompt, and session options are rejected"). A user who put `-p` into the default Arguments is not covered by any source read. Which exact command line a given install runs is unverified (test 1).
- Consequence for #386: the provider-terms path "interactive `claude`" applies, not the `claude -p` path. The exact command line Orca runs is not printed by the CLI; see the test list.

### 2. Does a local schedule fire while the Orca app is closed?

Answer: No, per source. The documentation does not state it (unverified in the docs).

- Docs: silent for local automations. Related statements: a Remote Orca Server "must stay awake" and its lifetime is "While the desktop app is running" or "While the foreground process or service is running" for `orca serve` (https://www.onorca.dev/docs/remote-servers, table "Desktop app or orca serve?" and the section "Use the remote server"). The CLI overview says the CLI scripts "a running Orca editor" (https://www.onorca.dev/docs/cli/overview).
- Source: the scheduler is an in-process timer in the Orca main process: a 60 second interval ([service.ts#L46](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L46), [#L126](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L126)). A search of `src/main/automations`, `src/main/persistence/scheduling-automations` and `src/shared/automation-*.ts` for `launchd`, `crontab`, `systemd`, `schtasks` found no operating-system scheduler (one comment about crontab syntax only). So a closed app, a quit app, or a sleeping computer runs nothing; the next start catches up per the grace rule below.
- Window closed but process alive (source): `shouldQuitWhenAllWindowsClosed` returns true on Linux and Windows, and on macOS only when quitting; in serve mode it returns false unless quitting ([window-all-closed-quit-policy.ts#L4-L9](https://github.com/stablyai/orca/blob/v1.4.237/src/main/startup/window-all-closed-quit-policy.ts#L4-L9)). On macOS the process may stay alive with no window. Then a due scheduled run is recorded as `skipped_unavailable` with the error "No Orca window was available to launch the automation." ([dispatch-refusal.ts#L19](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/dispatch-refusal.ts#L19), used at [service.ts#L281-L289](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L281-L289)).
- Headless: only a serve-mode process (`orca serve`) uses the headless dispatcher, which needs no window ([main-process-automations.ts#L19](https://github.com/stablyai/orca/blob/v1.4.237/src/main/startup/main-process-automations.ts#L19), [runtime-automation-service.ts](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/runtime-automation-service.ts)). The docs describe `orca serve` as the way to run "without the desktop window" (https://www.onorca.dev/docs/remote-servers, section "Alternative: orca serve").
- Not checked: whether Orca registers a background or tray process that keeps running after the last window closes on Linux. Source says the app quits; no documentation page mentions it.

### 3. What does the missed-run grace window do?

Answer (source; the docs only show the flag): a run that was due while Orca was not running is still started at the next check if it was due no longer ago than the grace window (plus a two-tick tolerance); older than that, it is recorded as a skipped run and not started. Default 720 minutes.

- CLI help: `--missed-run-grace-minutes <n>  Missed-run grace window`. Nothing more. Docs: one example, `orca automations edit <automationId> --missed-run-grace-minutes 30 --json`, under the heading "Missed-run grace" (https://www.onorca.dev/docs/cli/automations). Neither states the default, the unit meaning, or the behavior.
- Live read-only output: `orca automations list --json` shows `missedRunPolicy: "run_once_within_grace"` and `missedRunGraceMinutes: 720` on automations created in the app UI. The type allows only that one policy ([automations-types.ts#L8](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/automations-types.ts#L8)); the create default when the flag is omitted is 720 ([automation-definition-operations.ts#L120](https://github.com/stablyai/orca/blob/v1.4.237/src/main/persistence/scheduling-automations/automation-definition-operations.ts#L120)).
- Source rule: `missedBeyondGrace` is true when `now - scheduledFor > graceMinutes * 60 s + 2 * tick` with tick 60 s ([dispatch-refusal.ts#L161-L170](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/dispatch-refusal.ts#L161-L170)). In that case the run is stored with status `skipped_missed` and the error "This run was past its missed-run grace window when Orca next checked." ([dispatch-refusal.ts#L184-L186](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/dispatch-refusal.ts#L184-L186)), and the schedule advances ([service.ts#L271-L274](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L271-L274)).
- Catch-up count (source): the check takes only the latest occurrence at or before now (`getLatestAutomationOccurrence`, [service.ts#L266](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L266)), runs or skips that one, then advances to the next future occurrence ([service.ts#L299](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/service.ts#L299)). Earlier missed occurrences in the same downtime are not replayed and no row was found being written for them in that code path (read of those lines; behavior not tested).
- Consequence: grace is measured from the latest missed occurrence only. A schedule that fires more often than the grace window (for example a 20 minute issue pickup with the 720 minute default) always finds a latest occurrence younger than the grace after any downtime, so it gets exactly one catch-up run and never a `skipped_missed` row. Only schedules whose interval exceeds the grace (for example a daily run with grace 30) can produce `skipped_missed`. Derived from the two rules above, not tested.
- The tag-time comment on `missedBeyondGrace` (read at the tag, paraphrased) says: grace is a downtime catch-up budget; the two-tick tolerance exists so scheduler latency does not count as downtime; a zero-grace run that came due during an outage shorter than the tolerance is dispatched, not skipped; and a long precheck or worktree create in serve mode can make a pass longer than the tolerance and mis-skip a later automation.

### 4. Can `automations edit` enable or disable an automation, and which fields does it change?

Answer: yes. `--enabled` or `--disabled`; both together are refused.

- CLI help for `orca automations edit`: option lines `--enabled  Enable the automation` and `--disabled  Disable the automation`; example `$ orca automations edit 2f9e... --disabled`. Docs: `orca automations edit <automationId> --enabled --json`, and "Use edit to change the name, prompt, provider, target, schedule, or enabled state." (https://www.onorca.dev/docs/cli/automations, section "Review and enable").
- Source: `edit` builds one update object from the flags below; only flags that are given are sent ([automations.ts#L233-L253](https://github.com/stablyai/orca/blob/v1.4.237/src/cli/handlers/automations.ts#L233-L253)). `--enabled` with `--disabled` fails with "Use either --enabled or --disabled, not both." and a value on either flag is rejected ([automation-handler-flags.ts#L168-L183](https://github.com/stablyai/orca/blob/v1.4.237/src/cli/handlers/automation-handler-flags.ts#L168-L183)).
- Fields `edit` accepts (CLI help for `edit`): `--name`, `--prompt`, `--provider`, `--extra-agent-args=` (empty clears), `--precheck`, `--precheck-timeout`, `--repo`, `--workspace`, `--project`, `--host`, `--project-host-setup`, `--source-context <json|null>` (null clears), `--workspace-mode`, `--base-branch`, `--trigger` or `--schedule`, `--time`, `--day`, `--timezone`, `--enabled`, `--disabled`, `--missed-run-grace-minutes`, `--reuse-session`, `--fresh-session`. Identity: `edit <id>` or `--id <id>`. The usage line shows only `--name` and `--trigger`; the option list is the complete set.
- Not shown in the `edit` help (source only): `--precheck` with an empty command passes `null` and removes the precheck ([automation-handler-flags.ts#L220-L238](https://github.com/stablyai/orca/blob/v1.4.237/src/cli/handlers/automation-handler-flags.ts#L220-L238), read of the empty-command branch); the docs and help do not say so.
- Not changeable by `edit`: the id, creation time, run history. `remove` deletes an automation "and its run history" (CLI help).

## Exact `automations` surface (Orca CLI 1.4.237)

Commands (from `orca automations --help`): `list`, `show`, `create`, `edit`, `remove`, `run`, `runs`. There is no `precheck` subcommand and no `pause` or `resume`; enabling and disabling is `edit --enabled|--disabled` or the `--enabled|--disabled` flag on `create`.

Flags common to all subcommands (each `--help`): `--help`, `--json`, `--pairing-code <code>` (run against a remote Orca server using an `orca://pair?...` code), `--environment <selector>` (saved paired Orca server, id or name), and for `show`, `edit`, `remove`, `run`, `runs` also `--id <id>`.

## Precheck contract

What CLI help and docs state:

- `--precheck`: "run a bounded command before scheduled runs; exit code 0 continues, anything else records a skipped run." (CLI help for `create`, Notes). Docs: "Skip scheduled work when a cheap shell probe fails (non-zero exit records a skipped run)". `--precheck-timeout` has no description in help; docs do not mention it.

What the source states (none of it is in the docs):

| Item | Behavior | Source |
|---|---|---|
| Pass rule | Passes only if not timed out, no spawn error, and exit code exactly 0. | [automation-precheck.ts#L31](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/automation-precheck.ts#L31) |
| Timeout | Default 60 s, maximum 600 s, minimum 1 s (values are floored and clamped). The CLI refuses `--precheck-timeout` above 600 and refuses it without `--precheck`. Unit is seconds. | [automation-precheck.ts#L3-L11](https://github.com/stablyai/orca/blob/v1.4.237/src/shared/automation-precheck.ts#L3-L11), [automation-handler-flags.ts#L224-L242](https://github.com/stablyai/orca/blob/v1.4.237/src/cli/handlers/automation-handler-flags.ts#L224-L242) |
| Timeout handling | The process group is sent SIGTERM, then SIGKILL after 2 s (POSIX); `taskkill /t /f` on Windows. Recorded as timed out, exit code null. | [precheck-runner.ts#L79-L131](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/precheck-runner.ts#L79-L131) |

| Working directory | The project path of the automation's resolved host setup (`setup.path`), not the per-run or existing worktree. | [run-target-resolution.ts#L223](https://github.com/stablyai/orca/blob/v1.4.237/src/main/automations/run-target-resolution.ts#L223) |

## How a skipped run is reported

Source behavior; the docs say only "records a skipped run".

| Cause | Run status | `error` text | Shown by CLI as |
|---|---|---|---|
| Precheck exit code not 0 | `skipped_precheck` | `Precheck exited with code <n>.` | `Skipped run <id> (skipped_precheck).` after `run`; a line `<run id>  <automation id>  <status>  <trigger>  <scheduledFor ISO>` plus title, `precheck: exit <n>; <stderr or stdout>`, `error: ...` in `runs` |
| Precheck timed out | `skipped_precheck` | `Precheck timed out after <n>s.` | as above, `precheck: timed out; ...` |
| Precheck could not start | `skipped_precheck` | `Precheck failed: <message>` | as above, `precheck: error; ...` |
| Past grace when Orca next checked | `skipped_missed` | `This run was past its missed-run grace window when Orca next checked.` | `Skipped run ... (skipped_missed).` |
| No Orca window to launch the agent (desktop process without a window) | `skipped_unavailable` | `No Orca window was available to launch the automation.` | same |

## What changes for #386 (facts only)

- By source, the agent runs as the user's own interactive `claude` or `codex` TUI in an Orca terminal, with the prompt as an argument (documentation silent on `-p`; test 1 confirms). The `claude -p` provider-terms path does not apply to Orca automations.
- By source (documentation silent), a local Orca schedule is only as live as the Orca process. A cron or systemd job outside Orca, or `orca serve` on an always-on host, is the documented way to run without the desktop window.
- Grace default is 720 minutes; one catch-up run per missed stretch (source). A frequent schedule (the 20 minute pickup) never yields `skipped_missed`; it gets one catch-up run after downtime.
- `edit --enabled|--disabled` exists and is scriptable, so a template adapter can disable without deleting.
- Precheck (source-read only, not tested): the working directory is the project root path, the environment is the Orca main process environment, the timeout is 1 to 600 s with 60 s default, and it is not run for manual runs. A template precheck should not depend on the worktree path or on the user's shell profile until tests 5 and 7 confirm this.

2. App closed, local schedule. Create an enabled automation with `--trigger "*/5 * * * *"` (every 5 minutes) and a precheck of `date >> <a file in the throwaway project>` so each tick leaves a trace. Quit Orca fully (Quit from the menu, not only the window close). Wait 15 minutes. Start Orca. Pass (source prediction): the file has no lines for the closed period, and the Runs list shows a single catch-up run after start, with no `skipped_missed` row (the 5 minute interval is shorter than the default grace). 3. Grace window. Create an enabled automation with an hourly trigger at a fixed minute X (for example `--trigger "30 * * * *"`), a trivial precheck that appends the time to a file, and grace 5 minutes.
