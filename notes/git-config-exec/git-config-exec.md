# Git configuration that runs code or redirects the network inside a repository

Research for issue #376 (part of #372), feeding the decision in #289. Throwaway note on branch `research/git-config-exec`, not meant to be merged.

## Question

Which git configuration keys and files are documented to execute code or redirect a connection, which commands of Update all trigger them, which documented switches let a caller neutralize them, and which of those switches would also break a legitimate per-repository deploy key or the user's own hooks.

## Short answer

- Code runs from four places: hooks (`.git/hooks` or `core.hooksPath`), programs named in config (`core.fsmonitor`, `core.sshCommand`, `credential.helper`, `core.gitProxy`, `core.askPass`, `gpg.program`, `remote.<name>.vcs`, `remote.<name>.uploadpack` and `receivepack`), content filters (`filter.<driver>.clean`, `smudge`, `process`), and diff drivers (`diff.external`, `diff.<driver>.textconv`). Attribute files only name a driver; the command always comes from config.
- Redirection comes from `url.<base>.insteadOf`, `url.<base>.pushInsteadOf`, `remote.<name>.url`, `remote.<name>.pushurl` and `remote.<name>.vcs`.
- Documented switches exist for hooks (`-c core.hooksPath=/dev/null`), `core.fsmonitor` (`-c core.fsmonitor=false`), credential helpers (`-c credential.helper=` resets the list), filters (an empty command), push URLs (`-c remote.<name>.pushurl=` clears the list), `core.sshCommand` (override it) and automatic maintenance. `--no-verify` is not a general switch: it skips only `pre-commit`, `commit-msg` and `pre-push`.
- No documented switch removes a repository's `url.<base>.insteadOf`, a `remote.<name>.vcs`, an `include.path`, or turns off includes for commands other than `git config`. The caller can only read the resolved value (`git remote get-url [--push] <name>` expands `insteadOf`) and refuse it.
- A deploy key that lives in `core.sshCommand` (or a token in a local `credential.helper`) is exactly what the switches for those two keys replace. Switching off hooks breaks the user's own hooks but not a deploy key. `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` never touch the repository's own config, so they do not address #289 and would drop the user's global signing, helper and ssh settings.
- Hooks also run on commands outside the ones #289 lists: `fetch`, `status` and `add` fire `reference-transaction` and `post-index-change` in the observed run. The pin in `app/src/projects.mjs` (`:426-428`) covers `worktree add`, `commit` and `push`. The unpinned `add -A` and `status` run inside the worktree, which holds origin's files: with a relative `core.hooksPath` (for example `.hooks`) they ran the hook committed to origin's tree, not the checkout's (observed). That is the code path the pin's own comment says it prevents. With `core.hooksPath` unset or absolute the hooks come from the checkout's `.git` and the same commands run those.

## Method

- Documentation: pages of https://git-scm.com/docs as served on 2026-10-27 (latest-version manual; the git-config page reads "last updated in 2.56.0"; pages: git-config, githooks, gitcredentials, gitattributes, git, git-fetch, git-push, git-commit, git-worktree, git-remote, git-maintenance, git-gc, git-remote-ext, gitrepository-layout). Anchors below are the page's own ids.
- Local runs, marked "observed": git 2.56.0 on Linux, in a throwaway folder inside the worktree (deleted afterwards), with `HOME`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` isolated. Remotes were local bare repositories, a `127.0.0.1` server that answers 401, and `.invalid` hosts that are never contacted because the configured program replaces the connection. No other repository and no network were touched.
- Update all's git calls (read from the code): `fetch -q origin <base>` (`app/src/projects.mjs:193`, `:242`), `ls-remote [--symref] origin ...` (`:201`, `:238`, `:465`), `worktree add` (`:443`), `add -A` and `status --porcelain` (`:451`, `app/src/git.mjs:129` via `clean`), `commit -q -m` (`:456`), `push -q -u origin <branch>` (`:467`), plus `rev-parse`, `symbolic-ref`, `remote get-url`, `config --get`, `branch -D`, `worktree remove`, and in `app/src/git.mjs` `add`, `write-tree` through a temporary index. Every call carries `-c core.fsmonitor=false` (`git.mjs:57`); commands outside `NO_FILTER` get filter-driver overrides (`git.mjs:24-57`); network calls get `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=''` and, only when `core.sshCommand` and `GIT_SSH_COMMAND` are both unset, `GIT_SSH_COMMAND='ssh -o BatchMode=yes'` (`projects.mjs:181-185`).

## Caller-side switches

- `-c <key>=<value>` is the highest precedence and beats `GIT_CONFIG_COUNT` pairs, which beat every config file ([GIT_CONFIG_COUNT](https://git-scm.com/docs/git-config#Documentation/git-config.txt-GITCONFIGCOUNT)) [doc, obs].
- Pairs have an advantage over `-c` for filter drivers: a `-c` option splits at the first `=`, so it cannot name a driver whose name contains one; pairs carry key and value separately. `app/src/git.mjs` already uses them. In this run `-c filter.x.clean=` also worked for a simple name.
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM` replace or skip only the global and system files ([git](https://git-scm.com/docs/git#Documentation/git.txt-GITCONFIGGLOBAL)). They are protected scopes, so the repository's config stays in force: [obs] a repository hook ran with `GIT_CONFIG_GLOBAL=/dev/null`. They are the right tool for a clean test environment, not for #289.
- `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_ASKPASS`, `GIT_EXTERNAL_DIFF`, `GIT_EXEC_PATH` and `GIT_TEMPLATE_DIR` belong to the caller's environment, not to the repository. `PATH` decides which `git-remote-<vcs>` or `git-lfs` runs.
- Nothing in the documentation disables local config as a whole. A caller that must ignore repository-local network config has to override each key it knows, and the list above is the documented set; a new git version can add keys.

## Observations about Update all (read against the code)

- `projects.mjs:426-428` does not switch hooks off. It rewrites a relative `core.hooksPath` to an absolute path in the checkout, for `worktree add`, `commit` and `push` only, so the fetched tree's hooks do not run. `fetch` (`:193`, `:242`) runs with `-C <checkout>`, where a relative path already resolves to the checkout, so it is not the gap.
- The gap is `git(ctx, tree, ['add', '-A'])` (`:451`) and `clean(ctx, tree)` (`:454`, `git.mjs:129`): both run inside the worktree without the pin. Experiment with a relative `core.hooksPath=.hooks`, a different `post-index-change` committed to origin and another in the checkout: pinned `worktree add`, `commit` and `push` ran only the checkout's hooks; unpinned `add -A` and `status` in the worktree ran the hook from origin's tree (observed). The row "The repository's `core.hooksPath` is pinned for worktree, commit and push" in `docs/security.md` names the covered commands and is silent on these two. `ls-remote` and `diff-tree` fired no hook in the runs; `rev-parse`, `cat-file`, `ls-tree`, `branch -D` and `worktree remove` were not run.
- `quiet()` sets `GIT_SSH_COMMAND` only when `core.sshCommand` is unset (`projects.mjs:183`), so it does not replace a repository's deploy key. It also never neutralizes a repository's `core.sshCommand`, which is the open item of #289.
- `githubRemote` (`git.mjs:131`) checks the host of `git remote get-url origin` (without `--push`). That value is already `insteadOf`-expanded (doc, obs), so a local rewrite to a non-GitHub host stops the push and PR. It does not check `remote.origin.pushurl`: [obs] `push` goes to `pushurl` regardless of the URL checked. `remote.origin.vcs` is not checked either.
- `diff-tree -r --name-status` and the `NO_FILTER` list match what the run showed: no filter, textconv or external diff ran for them.

## Unverified

- `GIT_ASKPASS` and `core.askPass`: in this environment the askpass program was not started for a 401 on http, not even with `GIT_ASKPASS` set to an absolute script path, so the ordering in gitcredentials and the effect of an empty `GIT_ASKPASS` (`projects.mjs:182`) were not confirmed. Cause unknown.
- Whether the `pre-auto-gc` hook fires from `fetch`'s automatic maintenance. The maintenance run was observed (trace), the hook from that path was not.
- `reference-transaction` from `branch -D` and `worktree remove`, and any hook from `ls-remote` beyond "none observed".
- `url.<base>.insteadOf` for a URL given explicitly instead of the remote name; the rewrite was tested through `origin` only.
- Behavior of `remote.<name>.uploadpack` and `receivepack` over ssh (documented as the remote-side program; not run).
- `safe.directory` and the ownership check (needs a second user account).
- `protocol.ext.allow=always` in a repository's own config permitting `ext::` URLs: the default is documented (`ext` is `never`), the override and the command execution were not run.
- Whether ssh options in the user's own ssh client config (a `Host` alias with `IdentityFile`) carry a deploy key that survives a `core.sshCommand` override. That is ssh_config, not git documentation, and was not checked.
- Submodule fetch behavior; no populated submodule was tested.
- Behavior in git versions other than 2.56.0.
